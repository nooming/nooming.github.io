# 更新日志写法

## 目标

三秒看懂一个版本：发生了什么，影响到哪里。像一条干净的动态，不像一份发布说明书。

## 结构

- 版本标题：`## v2.4 · 2026.10`；未发布用 `## 未发布 · 2026.11`。
- 标题下先写一句摘要（`>` 引用），说清这一版的主题，不写「重磅」「震撼」。
- 大版本按主题分组：`设计系统`、`阅读与工具`、`独立项目`；小版本用 `新增 / 改进 / 修复 / 移除`。
- 每条只写一个变化，控制在 1–2 行。
- 技术路径、内部模块名只在能帮助定位时保留；否则写用户看到的结果。
- 提交索引放在文末统一维护，不塞进每个版本正文。

## 语言

- 先写结果，再写实现。例如「离线也能本地优化」，而不是「重构了 optimizer 调用链」。
- 动词开头，句子短；一条里不要叠三个以上逗号。
- 不写 emoji、感叹号、「一键」「无缝」「浏览器内演算」「文件不上传」等套话。
- 不用「我们」；不解释动机，只交代变化。
- 数字只保留有意义的：版本、日期、数量、性能提升。
- 中英文之间留空格；` · ` 用来分隔同一层级的短信息。

## 示例

```md
## v2.6 · 2026.12

> 把工具页的加载、空状态和错误提示补齐。

### 改进

- 工具首页搜索支持按分组过滤，清空后恢复全部。
- 文档转换在浏览器不支持时给出降级说明，不再静默失败。

### 修复

- 修复刷新后工具页主题闪白。
```

## 归档

重写历史版本前，先把原文完整复制到 `CHANGELOG-legacy.md`，再在新文件里压缩。不要在原文上直接删细节。
